# Экспорт регионов — R2

Сцены редактируются вручную в Godot. Общий инструмент собирает их геометрию и маркеры,
проверяет результат настоящим серверным загрузчиком и публикует один атомарный пакет.
Рабочая БД, запущенный сервер и исходные сцены при экспорте не изменяются.

## Запуск

Обычный Development-запуск сервера автоматически проверяет сохранённые сцены и
обновляет пакет при изменениях. Дополнительная команда перед игрой больше не нужна:

```powershell
$env:DOTNET_ENVIRONMENT = 'Development'
dotnet run --project Content.Server
```

При актуальном пакете Godot/exporter не запускаются. При устаревшем, отсутствующем или
повреждённом пакете сервер вызывает общий инструмент, проверяет результат и продолжает
запуск с новым пакетом. Ошибка экспорта останавливает запуск до открытия БД/порта;
предыдущий пакет сохраняется. Проверка источников требует сохранённых на диск сцен.
Уже запущенный сервер после изменения карты нужно перезапустить; live reload не введён.

Автоматизация работает только в локальном checkout и только для стандартного пакета.
Standalone-сервер и явно заданный альтернативный `RegionExports:PackagePath` сохраняют
обычную загрузку готовых данных. `--validate-content` остаётся проверкой без публикации,
поэтому вложенная проверка экспортёра не вызывает повторный экспорт. При необходимости
автоматику можно явно отключить через `RegionExports:AutoExport=false`.

Ручной экспорт для диагностики/CI по-прежнему доступен из корня репозитория:

```powershell
.\tools\Export-Regions.ps1
```

Если Godot не найден автоматически:

```powershell
.\tools\Export-Regions.ps1 -GodotPath D:/Godot_v4.7.1-stable_mono_win64/Godot_v4.7.1-stable_mono_win64_console.exe
```

Команда собирает клиент и отдельную серверную сборку в `.artifacts/region-export/build`,
затем запускает headless Godot и серверный `--validate-content` без порта/БД.
`-CheckOnly` повторяет экспорт и сравнивает опубликованный JSON без публикации.
`-NoBuild` допустим только при актуальных клиентской и изолированной серверной сборках.
Одновременные публикации защищены файловой блокировкой.

В Godot можно открыть `Scripts/Editor/Regions/ExportRegionsInEditor.cs` и выполнить File → Run.
Сначала сохранить изменённые сцены. Старые F6-сцены ExportRiverLanding/ExportRiverCity
вызывают тот же общий инструмент; частичного обновления одного региона больше нет.

После ручного экспорта перезапустить Development-сервер обычным способом и запустить игру.
Уже запущенный сервер держит прежний пакет в памяти: live reload этим этапом не вводится.

## Что редактировать

- `Content.Client/Scenes/Regions/RiverLanding/RiverLandingBlockout.tscn` — пристань.
- `Content.Client/Scenes/Regions/RiverCity/RiverCity.tscn` — город.
- `Content.Server/Data/region-authoring.json` — список экспортируемых сцен и привязки
  существующих серверных имён к UUID маркеров. Переименование Node не меняет привязку.
- `Content.Server/Data/regions.json` — приватные правила мира и маршруты. Они проходят
  обычную проверку сервера при каждом экспорте и запуске, но не попадают в клиентский PCK.

`outskirts` пока остаётся существующим регионом из серверных данных. Демонстрационные
Prototype/Outskirts scenes из R1 не подменяют его действующую карту. Их перенос — R3.

`Content.Server/Data/Regions/region-package.json` — генерируемый опубликованный результат.
В нём все актуальные геометрии, UUID, привязки и отпечатки источников. Не редактировать вручную.
Старые отдельные river-landing/river-city JSON сохранены для legacy fixtures и совместимости;
штатный сервер при `RegionExports:PackagePath` использует геометрию и размещения из пакета.

## Проверки и публикация

Проверяются структура сцены, уникальные UUID, конечные координаты, разрешённые формы,
непротиворечивая классификация коллизий, размер карты и walkable placements. Для города
все привязанные точки должны быть достижимы от Spawn. Gate/arrival bindings проверяются
по типу маркера, радиусу и существующим правилам общего графа переходов.

Текущий backend остаётся плоской сеткой с прежним лимитом 6144 клетки и прежним wire
протоколом. Маркеры квантуются до миллиметра; геометрия растеризуется в метровые клетки.
Неизвестные формы/повороты/масштабы вызывают ошибку с путём узла.

Сборка кандидата идёт в `.artifacts`. Ошибка геометрии, зависимости или серверной проверки
не заменяет действующий пакет. После успешной проверки публикуется один JSON через
атомарную замену файла; читатель получает полный старый или полный новый набор.
Формат не содержит времени сборки/абсолютных путей; порядок сцен/маркеров канонический.
CRLF/LF и UTF-8 BOM не меняют отпечатки текстовых исходников.

В рабочем checkout сервер проверяет исходники до запуска. При автоматическом запуске
устаревший экспорт обновляется; в режиме проверки/при отключённой автоматике выдаётся
`Stale region export` с именем файла. У standalone сервера исходников Godot нет:
достаточно серверного пакета, а клиент продолжает проверять hash геометрии при входе.
Совпадение hash не заменяет серверную проверку действий игрока.

## Публичный артефакт

Параллельно создаётся реальный PCK в `.artifacts/region-export/client/<revision>.pck`.
В нём только manifest с region ID/scene path/geometry hash и самодостаточные визуальные
сцены. AuthoringAnchors, Preview, ScaleReferences и scripts исключаются. PCK открывается
заново, загруженные из него сцены проверяются на оставшиеся служебные узлы/скрипты.

Это пакет ресурсов регионов, а не полный release-клиент. Подключение этого PCK к игровому
scene loader и аудит полного release PCK относятся к следующему этапу. Текущий F5 продолжает
использовать авторские сцены с прежней проверкой геометрии; SQL, protocol, combat travel,
асинхронная загрузка и глобальный durability barrier этим изменением не меняются.

## Ручная приёмка

1. Сохранить сцену и запустить Development-сервер: изменённые данные экспортируются
   автоматически. Повторный запуск без правок не должен запускать Godot/exporter.
2. Переместить blocker в свободное место, не перекрывая NPC/входы; экспортировать,
   пересобрать сервер и проверить новый обход препятствия в игре.
3. Переименовать городской маркер без смены UUID: экспорт и серверная привязка сохраняются.
4. Назначить двум маркерам одинаковый UUID: экспорт должен отказать, опубликованный пакет
   остаётся прежним. Исправить сцену и повторить экспорт.
5. После правки сцены выполнить `--validate-content`: получить понятный отказ об
   устаревшем пакете. Обычный Development-запуск должен сам обновить пакет и продолжиться.

В production перенос/удаление persistent размещений требует отдельной политики миграции
(R6). R2 не меняет ID персонажей/предметов, формат сохранений или игровое поведение ворот.
