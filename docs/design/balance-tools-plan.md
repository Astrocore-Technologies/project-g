# План инструментов баланса и админа/ГМ

Статус: **исторический расширенный план, объём сокращён пользователем 2026-10-10**.
Текущая реализация — локальный редактор и изолированная тестовая площадка; права/регионы/audit/API отложены.
Актуальные границы: [ADR 0013](../architecture/0013-local-balance-workshop.md), [руководство и проверки](../development/balance-workshop.md).
Дальнейшие этапы ниже не запускаются автоматически.
Архитектура и варианты: [balance-tools-proposal.md](../architecture/balance-tools-proposal.md).
Документ подготовлен по запросу пользователя на план; он не означает автоматического запуска этапов и не заменяет план регионов.

## Результат для пользователя

Открыть Мечника, выбрать «Выпад», изменить урон со 120,0% до тестовых 130,0%, увидеть сравнение билдов, сохранить черновик и проверить его на отдельном сервере. В игре описание и реальный урон используют одну версию параметров. Числа примера не являются принятым ребалансом.

ГМ позже выбирает доступный регион, видит подготовленные операции и получает подтверждённый результат с записью в журнале. Общее изменение типа моба и локальная настройка событийного экземпляра — разные действия.

## Порядок этапов

| Этап | Результат | Критерий завершения |
| --- | --- | --- |
| B0. Зафиксировать базовый результат | Инвентаризация настраиваемых полей, единиц, скрытых сведений и чисел в C#/подсказках; набор эталонных билдов | Можно сравнить текущие расчёты до/после структурных изменений; существующие ошибки тестов отмечены отдельно |
| B1. Общие расчёты и CLI | `Content.Server.Rules` и headless validate/preview/diff инструмент | Сервер и калькулятор используют одни формулы; текущий каталог даёт тот же результат; клиент не зависит от Rules |
| B2. Разделить контент | Авторские файлы по категориям, manifest, deterministic package builder | Старые и собранные определения семантически совпадают; ID/числа сохранены; нет двух авторских источников |
| B3. Первый Balance Studio | Список навыков Мечника, формы, черновики, undo, ошибки, сравнение одного билда и цели | Полный сценарий изменения выпада выполняется без ручной правки JSON и C# |
| B4. Согласовать игровой UI | Параметризованные подсказки из разрешённых серверных значений | Изменённые cooldown/стоимость/урон совпадают в редакторе, симуляции и подсказке; секреты не раскрыты |
| B5. Проверка и выпуск | Пресеты 1/15/30, серверные сценарии, отчёт влияния, запуск изолированной среды, активация совместимого пакета при рестарте | Пакет воспроизводим, несовместимое сохранение обнаруживается до активации; возврат к совместимому пакету проверен |
| G1. Серверные команды сотрудников | Capabilities, scope, регион, очередь, receipts, audit; существующая консоль — adapter | Повтор/конфликт/нет прав/отказ БД/потеря ответа не дают лишнего эффекта; три прежние операции работают в разрешённом регионе |
| G2. Панель Operations | Приватный API, staff-сессии, список регионов, подготовленные операции и журнал | Действия доступны по правам; сервер подтверждает commit; панель показывает queued/completed/rejected/unknown |
| G3. Событийные сущности | Разрешённые шаблоны и per-instance overrides после решения gameplay-вопросов | Заданы награды, время жизни, restore/cleanup и ограничения; обычные сущности и определения не изменяются |

Рекомендуемая последовательность: B0 → B1 → B2 → B3 → B4 → B5, затем G1 → G2 → G3. Серверную модель G1 можно проектировать раньше, но она не нужна для первого редактора. Горячая замена общего баланса идёт отдельным проектом после этой цепочки.

## B0–B2: подготовка без изменения баланса

Области: `Content.Server/Data`, `Stats`, чистые определения `Progression/Professions/Combat`, новая библиотека Rules и CLI, content-copy/build конфигурация, соответствующие тесты.

- Составить карту: поле → источник → единица → формула → зависимые сущности → отображение игроку. Проверить все числа в SwordsmanUi и фактическое использование полей, включая дубли `range`/`rangeFactor`.
- Отдельно пометить технические guards и игровые параметры. Не превращать лимиты пакетов/очередей в балансные настройки для дизайнера.
- Для исходных билдов сохранить точные результаты и версии правил. Предыдущий прогон 2026-10-10 имел падение `RecoveryReplicationTests.TwoLossyClientsReplaceDeadNpcOnlyAfterDurableRespawn`; перед приёмкой новых изменений установить актуальный baseline и разобрать сохраняющееся падение.
- Выделить чистые расчёты и граф их типов без изменения поведения. Stateful combat продолжает исполняться в Server.
- В CLI сначала читать существующий JSON. Затем выполнить одноразовое разделение и сравнить весь каталог, включая разделы вне первого UI. Ошибка останавливает переключение; старый источник хранится в Git.
- Предлагаемые команды CLI: `validate`, `preview`, `compare`, `build-package`. Это будущий интерфейс, исполняемых команд сейчас нет.

Проверка: build, существующие stat/content tests, совпадение эталонных результатов, duplicate/unknown/missing-reference/path traversal, round-trip без потери точности, reproducible hash, отсутствие серверных assets и assemblies в игровом export. Gameplay protocol и схема сохранений на этом этапе не меняются.

## B3–B4: минимальный законченный редактор

Первый вертикальный срез охватывает тренировочный меч, Мечника, его десять навыков и параметры, нужные для тестового билда. Остальные разделы при чтении/сохранении сохраняются и не теряют неизвестные редактору данные; неизвестную схему инструмент отказывается редактировать целиком.

Экран:
- Категории и поиск слева; выбранный объект и readable ID.
- Поля с единицами, подсказками, возможностью вернуть исходное значение.
- Справа исходные/новые статы и урон; блок ошибок с переходом к полю.
- Тестовые характеристики, оружие, профессия и цель в отдельной компактной панели.
- «Сохранить черновик», «Проверить», «Собрать тестовый пакет». Признак изменённого/невалидного черновика всегда виден.

Сохранение не применяет баланс к текущей игре. Проценты отображаются с одним десятичным знаком; изменение отображения не квантует внутренние коэффициенты. Начальные пресеты соблюдают доступные очки характеристик.

B4 затрагивает `Content.Shared/Network`, серверную проекцию известных навыков и клиентские подсказки. До кода перечитать network-protocol-change и godot-client-change skills. Обновить версию протокола и проверку совместимости; старый клиент получает понятный отказ. Локализация хранит шаблоны/названия, сервер передаёт разрешённые типизированные числовые параметры.

Приёмка:
1. Изменить коэффициент выпада в черновике, увидеть изменившийся урон; отменить — получить исходный результат.
2. Ввести недопустимую стоимость — увидеть конкретную ошибку, пакет не создаётся.
3. Изменить файл снаружи — Studio обнаруживает конфликт и не затирает правку.
4. Открыть/сохранить без правок — исходные коэффициенты и остальные разделы не меняются.
5. Запустить собранный тестовый пакет: подсказки известного навыка и фактическое исполнение согласованы, закрытый навык не раскрыт.

## B5: измеримый баланс

Добавить сценарии: серия автоатак по манекену; заранее заданная ротация Мечника с исчерпанием выносливости; применение навыка по защищённой цели; блок и восстановление. Сценарий исполняет настоящий серверный fixed tick; ожидание времени может ускоряться в тестовом runner, но формулы/порядок исполнения не меняются.

В отчёте: версии/seed/допущения, DPS автоатаки, урон ротации, время до истощения и восстановления, time-to-kill только когда цель убита за выбранный горизонт. Если не убита — показать остаток HP/истечение горизонта, а не выдуманное число. Пресеты помогают заметить сильную разницу между билдами; они не доказывают общий баланс игры.

Публикация сначала при рестарте: preflight на копии сохранений, выбранный hash, журнал активации, штатная остановка, запуск совместимого build/package. Кнопки активации Production нет в первом локальном редакторе. Правила пересчёта уже существующих персонажей описываются для конкретного изменения до выпуска.

## G1–G3: управление живым миром

G1 использует существующие `LiveDmInbox`, `ServerWorld.ApplyLiveDm`, regional routing и Database adapters как точки перехода. Авторизация на сервере, actor из проверенной identity, request ID и expected revision обязательны. Консоль и будущая панель используют одинаковые обработчики. Операция всегда адресована региону; случайное применение к primary world исключается.

Persistence: additive модели receipts/audit/event instances по мере необходимости; runtime IDs не заменяют persistent IDs. Схема SQLite/PostgreSQL и правила восстановления проверяются отдельно. До миграции установить retention и верхние бюджеты очередей, входных/выходных данных, pending-команд, журналов и событий. Конкретные лимиты — конфигурируемые технические параметры, подтверждённые нагрузочной проверкой.

G2: сначала read-only список регионов/операций, затем выполнение трёх существующих действий. Private API и staff auth принимаются перед реализацией этой границы. Для Production удалённый доступ остаётся выключенным до готовности identity/TLS/session revocation. Панель получает фильтрованные snapshot DTO; сетевой поток не читает изменяемые коллекции симуляции напрямую.

G3 зависит от gameplay-решений о событийных мобах и полномочиях ГМ. Первая подходящая операция после их принятия — создать один разрешённый шаблон события с ограниченным числом мобов и определённым завершением. Изменение HP существующего моба требует отдельной политики текущего HP; «отмена» не удаляет уже полученные игроками последствия.

Проверка: нет прав/чужой регион/отозванная сессия, stale revision, повтор с тем же/другим payload, переполнение очереди, рестарт после commit до ответа, rollback БД, audit consistency, региональное AOI, восстановление событий и сроков, закрытая информация в ответах. Тяжёлые чтения/отчёты и файловые операции не выполняются на fixed tick.

## Общие последствия

| Область | Планируемое влияние |
| --- | --- |
| Authority | Мир и применение баланса остаются серверными; preview не является командой изменения персонажа |
| Protocol | B0–B3 без изменения игрового wire; B4 — разрешённые поля навыков с новой версией; G2 — отдельный административный контракт |
| Persistence | B0–B4 без изменения персонажей; активация проверяет совместимость; G1+ добавляет необходимые audit/receipt модели через существующую Database |
| Performance | Preview/сборка офлайн; GM-команды bounded и по региону; audit I/O следует существующему commit barrier; никакого обхода всех персонажей каждый tick |
| Mobile | Tools не экспортируются в игровой клиент; B4 добавляет только bounded данные известного контента, без полного каталога |
| Authoring | Сцены владеют размещением; JSON владеет определениями/балансом; Git владеет историей исходников |

## Следующий конкретный шаг

После принятия направления — B0 и B1: эталонные расчёты и общий калькулятор через CLI. Это проверит основу до создания большого интерфейса. Затем B2–B4 дают первый удобный редактор с проверяемым результатом в игре.

Проверка этого планового изменения: сверка с текущими исходниками, gameplay contract и ADR, проверка локальных ссылок и `git diff --check`. Build/игровые тесты для одних Markdown-документов не требуются и этим планом не объявляются пройденными.
