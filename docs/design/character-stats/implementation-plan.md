# GDD 03 — план реализации Character & Stats

Дата: 2026-10-20. Статус: **C1 реализован на изолированном стенде;
пользовательская приёмка впереди**. Пользователь разрешил реализацию командой «го».
Принятые правила не согласуются повторно. Экспериментальные коэффициенты
сохраняют свой статус; миграции рабочей БД не выполнялись.
Фактические изменения, проверки и ограничения: [отчёт C1](../../development/character-stats-c1.md).

Источники: [снимок GDD 03](gdd-03.md),
[архитектура](../../architecture/character-stats.md),
[gameplay contract](../gameplay-contract.md),
[GDD 01 и прямые решения](../combat-system/implementation.md),

План развивает текущую систему и не заменяет незавершённую приёмку Movement M5
или отложенные падения/динамику M7/M8.

## 1. Исходное состояние перед C1

В коде уже есть семь статов, WIS, начальные 10/18/+5, owner-only preview,
общие MP/Stamina, смерть/воскрешение, 60-секундный respawn, ресурсы 50/50/100%.
Есть крафт, торговля, личное поручение, исследование и социальные модули;
наличие этих механик не означает готовность их reward policies по GDD 03.

Фактический порог EXP — `level * ExperiencePerLevel`; текущий content задаёт
100. PvE penalty берёт процент текущего накопленного EXP, смена максимума
ограничивает ресурс вместо сохранения доли. Полного respec ledger и системы
world-unique достижений в изученных модулях нет.

Baseline чтения: protocol v77, content schema 24/balance 19,
CharacterState v2, SavedProgression v1, migrations до 0012. Номера перед
реализацией перепроверены. Это исходное состояние, не текущее описание после C1.
Теперь protocol v78, content schema 25/balance 19, Allocation v1 как дополнение
SavedProgression v1; SQL schema 12 сохранена. Учёт очков и параметризованная
power-кривая реализованы, A=150/B=4 проверены только в отдельном эксперименте.
Основной legacy-баланс не заменялся. Детальные результаты — в отчёте C1 выше.

## 2. Сверка источников и оставшиеся пробелы

Правила GDD 03 со статусом «ПРИНЯТО» уже согласованы и являются требованиями
реализации. C0 — инженерная сверка документов, кода и проверок, которую агент
выполняет самостоятельно; это не новый этап согласования геймдизайна.
Устаревший код или локальный пересказ не требуют повторного утверждения GDD.
Пункты ниже различают уже принятые правила, техническую работу и только те
пробелы, которые явно оставлены открытыми/экспериментальными в самом источнике.

Неопределённая интерпретация старого прогресса решается перед фактическим переносом соответствующих данных; wipe или destructive repair не следуют из этого плана |

Этот реестр не переутверждает GDD 03 или принятый бой. В C0 агент переносит
уже принятые правила в актуальный implementation-facing contract без повторных
вопросов пользователю. Только действительно новые постоянные правила требуют
отдельного решения в момент, когда без них нельзя завершить конкретное поведение.
Notion-снимок сохраняется без редакционного исправления истории.

## 3. Очерёдность и зависимости

| Этап | Проверяемый результат | Зависимости |
| --- | --- | --- |
| C0. Техническая сверка и baseline | Актуальные ссылки на принятые правила, baseline и fixture | Подготовка реализации; без повторного согласования GDD |
| C1. Очки, EXP curve и распределение — реализован | Новый герой → награда → несколько уровней → preview → распределение → reconnect; UI/UDP/SQLite проверены, пользовательская приёмка впереди | Принятые правила GDD 03 и боя; параметризация CS07 и совместимость legacy без угадывания истории |
| C2. Ресурсы и signed regen | Единый переход максимумов, дробные ресурсы, истощение на timeline и общая смерть | CS05/06/14; C1 для общего учёта |
| C3. Смерть и таверна | Правильный PvE penalty и durable respawn binding, полный возврат | C1/C2, CS08/13; существующие D044–D046 |
| C4. Полный respec | NPC quote → предупреждения → free/paid reset → reconnect без повторного платежа | C1/C2, CS12; кошелёк и atomic payment |
| C5. EXP по активностям и деление | Настоящие producers, receipts и согласованное распределение | C1, определения наград; CS11 для group/Echo |
| C6. Дополнительные очки достижений | Shared и world_unique: исполнение условия → одна выдача → общий пул | C1, CS10; extension checkpoint/claims |
| C7. Проверка баланса и полная приёмка | Сравнение билдов, UX/tools, regression, UDP/storage и rollout report | Все включаемые этапы; CS03/15 для финальной математики |

Порядок базовой поставки: **очки и EXP → ресурсы → PvE-смерть и таверна**.
C0 — самостоятельная техническая подготовка этой работы. После C2 можно отдельно
делать C4; в C5/C6 действующие правила реализуются, а конкретные недостающие
определения контента уточняются только для зависимого поведения. C7 измеряет
конечный результат; короткие проверки/демонстрации выполняются после каждого
среза, а не откладываются на финал. Искусственная параллельность изменений
одних и тех же progression/checkpoint файлов здесь не требуется.

## 4. Детали этапов

### C0 — техническая сверка и исходная проверка

1. Точечно обновить устаревшие разделы gameplay contract на основании уже
   принятых правил GDD 03 и D003–D008/D101; действительно открытые пункты
   отделить от требований, не повторяя вопросы о принятых правилах.
2. Сверить lifecycle, resource refresh, checkpoint, current protocol и bounds.
   Сопоставить каждый разрыв с принятой нормой GDD и местом исправления в коде.
   CS05 — готовое требование, CS07 — реализация формы с настраиваемыми числами,
   CS16 — подготовка совместимости. Не превращать их в общий запрет начала C1;
   экспериментальные числа сохраняют свой статус и не становятся server default.
3. Создать отдельные fixtures: чистый level 1; level 29 перед порогом; cap 30;
   gear/passive с меняющимися максимумами; old/corrupt progression; два игрока
   разных регионов. Рабочую БД не открывать.
4. Выполнить build, targeted baseline и content validation. Снять длительность
   tick/commit, записей в секунду и owner packet bytes в воспроизводимом
   сценарии. Существующие failures записать отдельно.

Готово: нет неявного gameplay default первого среза, baseline повторяем,
статусы факта/предложения/блокера понятны.

### C1 — минимальный вертикальный срез

Области: `Content.Server/Stats`, `Progression`, `World/ServerWorld.Progression`,
`Persistence/SavedProgression`, `CharacterState`; `Content.Shared/Network`;
`Content.Client/Scripts/Progression`, `UI/Screens/CharacterView.tscn`; Database;
`tools/Balance.Core` и существующий content catalog.

- Добавить явный allocation ledger с инвариантом earned = invested + available.
  Skill practice, профессии и история оборудования сохраняются.
- Реализовать чистую ExperienceCurve и Award; подключить согласованный первый
  reward producer. Тестовая выдача допускается только как fixture, не player RPC.
- Провести согласованную versioned миграцию Int64 EXP/счётчиков по необходимости;
  не менять индексы STR/AGI/VIT/INT/DEX/LUK/WIS. Обновить bounds и packet budget.
- Сохранить один серверный calculation path для preview и apply; prepare до
  мутации, актуальная конфигурация и revision на apply, publish после commit.
- В UI показать все семь статов, итоговые целые значения, доступные очки,
  причины ошибок, stale preview и ожидание server response.
- Converter работает сначала dry-run/fixtures; production data этим этапом
  автоматически не изменяется.

Готово: level 1 имеет 10×7 и 18 свободных; до level 30 получает 163 очка
создания/уровней. Multi-level выдаёт ровно +5 за уровень; cap не копит EXP.
Применение всего пула в один стат даёт 173 без дополнительных бонусов;
cancel не меняет сервер; reconnect не дублирует выдачу. Preview и apply
совпадают при одинаковой revision. Источники server-only остаются скрыты.

### C2 — изменение максимумов и signed regeneration

Области: `CombatResources`, `CombatSimulation` equipment/effects/health/mana/
defense/timeline/life; `AbilitySimulation`; persistent resource context и journal.

- Подключить один ResourceTransition ко всем реальным изменениям максимумов,
  включая эффекты, пассивки и поломку; не применять его второй раз на Ability.
- Выполнить выбранное oldMax=0 правило. Смена конфигурации умершего не воскрешает.
- Signed regen исполняется по времени; sets включают отрицательный rate даже
  при полном ресурсе. Интеграция границ исчерпания, расхода и смены rate идёт
  через действующий timeline. Политика пауз — только согласованная.
- Подключить отрицательный HP regen к общей смерти, журналу и penalty один раз.
  MP/Stamina останавливаются на нуле, Channel не делает неоплаченного pulse.
- Сохранить правила Cast 0/50/100%, HP-cost D126/D127, cooldown/charges, D101/D102.
- Измерить изменение частоты checkpoint. Не обходить ADR 0008 асинхронной
  публикацией ещё не сохранённых ресурсов.

Готово: 400/1000 → 200/500 и обратный переход по утверждённой политике;
одновременные equipment/effect changes не дают двойного scaling; отрицательный
regen работает на full/partial/empty, граница смерти не зависит от FPS/пакетов.
Rejoin после expiry effects не восстанавливает ресурсы случайно.

### C3 — PvE penalty и respawn binding

Области: `ServerWorld.Pvp`, `ServerWorld.Life`, региональный transfer,
`CombatSimulation.Life`, character persistence, таверны в региональном content,
`DeathView.tscn` и NPC UI.

- Отделить PvE penalty от PvP; вычислять от порога следующего уровня с согласованным
  округлением, ограничивая текущим EXP. Idempotency по persistent death episode.
- Ввести stable tavern binding и серверную услугу назначения. В данные вынести
  таверну/регион/проходимую точку, в сцене оставить редактируемое размещение NPC.
- Respawn спустя 60 с: снять обычные эффекты смерти, вычислить новые максимумы,
  установить 50% HP/MP и 100% Stamina. Revive остаётся отдельной операцией D046.
- Проверить путь к таверне в другом регионе на существующем checkpoint/transfer;
  состояние binding и death episode не теряется после restart.

Готово: при пороге 1000 и CurrentEXP 20 смерть забирает 20, при 200 — 50;
уровень не уменьшается, на cap штраф 0. Reconnect и повторный respawn request
не дают второго penalty/возрождения. Нет bound tavern — согласованный outcome,
а не произвольная скрытая телепортация. PvP правила не изменились.

### C4 — городской полный сброс

Области: progression allocation, существующие NPC/services и currency/inventory,
checkpoint receipts, editable окно услуги, CharacterView.

- Durable first-free flag/receipt, версия услуги/цены и quote revision.
- Перед подтверждением показать стоимость, возврат очков и последствия для
  оборудования/навыков; сервер заново проверяет NPC, distance, In Combat и build.
- Записать платёж, first-free flag, investments=0, available и ресурсный переход
  одним checkpoint. Повтор одного подтверждения не даёт второй платёж.
- Альфа использует валюту; альтернативный предмет полной модели подключается
  при готовом definition/источнике. Не вводить item economy в обход решения.

Готово: первый reset бесплатный после reconnect, второй списывает выбранную
цену ровно один раз; достижения сохраняются; отказ при stale quote/недостатке
денег/неверной локации не меняет билд. Не добавлен cooldown после сброса.

### C5 — реальные источники EXP и общее распределение

Области: World progression/crafting/trade/quests, exploration, world events,
Social, Echo, inventory operations, persistence receipts.

Подэтапы можно принимать независимо:

1. C5a: craft completion, личное discovery, exploration, текущая delivery quest
   и PvE — только после определения их reward magnitude и eligibility. Повтор
   recipe разрешён; retry того же source operation не создаёт второй EXP.
2. C5b: group/Echo distributor после CS11. Проверить party change, death/offline,
   owner/root attribution и delayed projectile. Не придумывать Echo level.
3. C5c: значимая торговля/логистика, каталоги квестов и Live-DM — после появления
   конкретных definitions и антиабуз-правил. ГМ запускает configured event,
   произвольный grant в игроковый runtime не добавляется.

Готово: каждое направление проходит producer → durable receipt → EXP → owner UI;
нет скрытого hourly cap, валидный craft всегда даёт положительную награду.
Наличие интерфейсов C5c без работающего контента не считается реализацией C5c.

### C6 — очки за выдающиеся достижения

Области: server-only achievement definitions/evaluation, reward issuance,
Database paired migrations и общий checkpoint, owner-facing result.

- Подключить хотя бы одно согласованное shared и одно world_unique достижение
  либо явно оставить этап неготовым до content definitions.
- Реализовать уникальные ключи области/occurrence, durable source receipts,
  index uniqueness, race handling без частичной выдачи; не использовать один
  региональный JSON как глобальную таблицу победителей.
- Очки входят в единый allocation ledger и возвращаются при C4. Скрытый trigger
  не оказывается в Shared, каталоге клиента или тексте отказа.
- Не вводить общий лимит бонусных очков и не объявлять Shared repeatable/one-time
  без решения CS10. World claims переживают обычный restart.

Готово: два допустимых героя получают shared независимо; из двух претендентов
world_unique выдача ровно одна по выбранному правилу победителя. Crash до/после
commit и retry не умножают очки и не теряют committed winner.

### C7 — баланс, инструменты и совместная приёмка

- BalanceStudio редактирует согласованные coefficients/curve/rewards через
  метаданные и server validation, с undo/redo и защитой внешних правок.
- Воспроизводимые билды: level 1/10/20/30, весь пул в каждый стат, смешанные
  атакующие/ресурсные/защитные; уровни 100/200+ только математический stress,
  не фактическое повышение alpha cap. Naked/обычная gear/защитная gear,
  положительные/отрицательные modifiers и временные изменения.
- Сравнить TTK/DPS, effective HP, MP/Stamina budget, темп EXP по активностям.
  Ориентир 20–40% naked mitigation не объявлять cap; sqrt-вклад не гарантирует
  ограниченную защиту на бесконечном уровне. Данные покажут trade-offs;
  изменение баланса требует решения автора, а не автоматического optimizer.
- Режим округления UI отделён от серверной точности. Проверить реальные окна
  при 1280×720/1920×1080, keyboard/mouse, modal input, reconnect и cleanup.
- Прогнать UDP с duplicate/reorder/loss/reconnect и измерить tick/commit/packets
  в том же сценарии C0. Зафиксировать оборудование и ограничения стенда.
- Подготовить миграционный dry-run/report, порядок запуска и rollback;
  применение к рабочей БД отдельно от тестового завершения.

Готово: полный набор включённых требований доказан; оставшиеся зависимости
явно перечислены. C0–C3 сами по себе не означают завершение GDD 03.

## 5. Матрица проверки

| Область | Минимальная проверка |
| --- | --- |
| Статы и формулы | Существующие StatCalculator/CombatStatModel tests + только новые инварианты: allocation, signed rate, resource transition, extremes/finite, отсутствие неожиданных связей INT/WIS |
| EXP | Порог на каждом уровне, multi-level, checked overflow, независимость от cap, cap без накопления, личные receipts и честный повтор craft |
| Мутации | Preview без мутации; stale quote; одновременная gear/effect change; атомарное apply/reset; отрицательные/oversized allocations |
| Бой | HP-cost 0/50/100, Channel paid time, crit/evasion/defense pipeline, regen death chronology, D101/D102, projectile snapshot и effect expiry |
| Жизнь | Penalty от порога, ноль/cap, одна смерть — один штраф, 60 с, revive/respawn отдельно, 50/50/100, tavern cross-region и unavailable binding |
| Persistence | Versioned round-trip, legacy dry-run, corrupt model/ledger, SQLite reopen/crash/rollback, owner/revision conflict, receipt+payment+points atomicity |
| World-unique | Два region contexts, одновременный claim, retry/crash до/после commit, отсутствие выдачи проигравшему |
| Protocol | Round-trip, malformed/truncated packets, exact count/order, Int64 bounds, MTU с envelope, incompatible handshake, owner-only и AOI/LOS |
| UI/tools | Одна editable scene для игры/preview, draft/cancel/apply, free/paid quote, реальные GUI clicks, число статов, ошибки/таймаут, undo/redo и реальный server calculation |

Для C# этапов: `dotnet build Game.slnx`, затем минимальные релевантные tests
`dotnet test Content.Tests/Content.Tests.csproj --filter ...`; имена фильтров
берутся из реально добавленных/затронутых tests, не из предположения.
Content validation выполняется текущим server entrypoint `--validate-content`.
Для UI — затронутая сцена и standalone preview в Godot с Mobile renderer;
headless smoke не заменяет графический прогон. На финале одна полная regression
после targeted checks; повторять её без новых изменений не требуется.

SQLite проверки исполняются на изолированных файлах. Live PostgreSQL требует
отдельного тестового подключения; отсутствие доступа явно означает «не
проверено», сборка адаптера не считается provider integration test.

## 6. Организация изменений и оценка

Один срез — небольшой набор согласованных code/data/protocol/model/UI патчей
и отчёт с командами, результатами, местами настройки и игровым сценарием.
Перед соответствующими изменениями применять repo skills:
`network-protocol-change`, `server-simulation`, `godot-client-change`,
`godot-ui-scenes`, `code-change-verification`. Новый фундаментальный boundary
сначала требует отдельного ADR; этот план его не предусматривает.

Объём C1–C3 средний/крупный: пересекает Server/Shared/Client/Database и timeline.
C4 зависит от UX и экономики; C5–C6 — от недостающих gameplay definitions.
Достоверную оценку часов всего GDD до C0 дать нельзя: объём trade/logistics,
Эхо-наград и достижений пока не определён. После C0 оценить базовый срез и
каждый зависимый подэтап отдельно по часам активной работы агента, без времени
ожидания решений/пользовательской приёмки.
