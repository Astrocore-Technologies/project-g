# Godot UI Scenes

## Основной результат

Рабочие UI и меню Project G собирай в Godot-сценах `.tscn`. Человек должен открыть сцену в редакторе, увидеть постоянную иерархию элементов и изменить компоновку, оформление и анимации без переписывания C#-конструктора интерфейса.

Эту же сцену используй в игре и в автономном предпросмотре. Пустой `.tscn` с единственным скриптом, который строит весь интерфейс в `_Ready()`, не выполняет это требование. Отдельный художественный макет, расходящийся с рабочим окном, тоже не заменяет рабочую сцену.

## Утверждённый визуальный эталон Project G

Пользователь утвердил четыре концепта в `art-source/ui/rework-2026-10-17/`. Перед работой над HUD или внутренним окном прочитай `docs/design/ui-rework-2026-10-17.md` и осмотри соответствующий PNG. Сохраняй композицию, пропорции, плотность, тёмные сине-зелёные материалы, тонкие золотые акценты, типографическую иерархию и качество арта; перекраска старой программной формы не считается выполненным редизайном. Рисованные персонажи, предметы и числа не заменяют gameplay-контракт и реальные данные.

Перед handoff сопоставь реальный рендер той же рабочей Godot-сцены с концептом при одном размере кадра. Визуальное соответствие проверяется отдельно от сборки и функциональных тестов; существенные расхождения указывай как оставшуюся работу. Покажи реальный игровой кадр. Новые окна продолжают этот же стиль с композицией под свой сценарий.
## Перед изменением

- Прочитай `AGENTS.md`, relevant gameplay contract и принятые решения по затронутому экрану. Используй `godot-client-change`; для нетривиального изменения также `implementation-strategy`.
- Изучи существующий экран, presenter/controller, открытие и закрытие, маршрутизацию input, тему и UI-компоненты. Уточни действия игрока, данные и состояния окна по текущему контракту, не придумывая игровые правила ради макета.
- Проверь `docs/architecture/ui-foundation.md` и `docs/development/ui-assets.md`. В проекте уже есть `Content.Client/UI/Theme/fantasy-skin.tres`, `art-catalog.tres`, `UI/Screens` и `UI/Workbench.tscn`; переиспользуй подходящие ресурсы.
- Учти существующий технический долг: часть `UI/Screens` служит примерочной, а `UiScreenLayout`, `UiComposition`, `UiWindow` и presenters могут строить layout кодом. При работе над таким экраном переноси его затронутую компоновку в рабочую сцену; не копируй этот подход в новый UI и не начинай несвязанный полный перенос интерфейса.

## Композиция сцен

- Отдельное меню или окно, HUD и самостоятельно переиспользуемый блок оформляй отдельными сценами. Например, `Inventory.tscn` инстанцирует общий `ItemSlot.tscn`, который подходит также торговле и добыче. Каждый простой Label не требует отдельного файла.
- Новые экраны размещай в `Content.Client/UI/Screens/`, компоненты — в `Content.Client/UI/Components/`, скрипты — в `Content.Client/Scripts/UI/`. Сохраняй существующий путь изменяемой сцены, например `Scenes/App/MainMenu.tscn`, если перенос не нужен задаче.
- Для окна/компонента обычно используй корень `Control`; размещение HUD поверх мира через `CanvasLayer` выполняй на уровне композиции интерфейса. Не помещай сетевую сессию, игрока или мир внутрь UI-сцены ради доступа к данным.
- Постоянные панели, кнопки, поля ввода, контейнеры, размеры, отступы и anchors сохраняй в сцене. Используй Containers, size flags и minimum sizes; фиксированные offsets оставляй там, где они осмысленны, например для привязки HUD к краям.
- Общий стиль задавай редактируемыми Theme/StyleBox/font/icon-ресурсами и theme type variations. Сначала используй существующий UI kit; выделяй недостающие компоненты в пределах задачи. Не строй весь будущий UI kit заранее и не меняй общий Theme из одного окна во время игры.
- Анимации открытия, закрытия и состояний, которые удобно править художнику, сохраняй в сцене через `AnimationPlayer` или подходящие ресурсы. Кодом управляй их запуском.
- Динамические списки создавай из `PackedScene` элементов и привязывай данные. Количество строк, содержимое слотов, runtime-анимации и специализированная отрисовка карты/графика могут управляться кодом; это не повод программно создавать весь постоянный layout.
- Не запускай генератор поверх вручную изменённой сцены. Сохраняй ручные правки и действующие ссылки на ресурсы.

## View, данные и команды

- View хранит ссылки на узлы и отображает переданное состояние; presenter/controller связывает её с клиентским состоянием и командами. Передавай действия через signals/events или явный API, без поиска `WorldController` из глубины виджета.
- C# отвечает за привязку данных, обработчики, валидацию ввода и переключение состояний. Кэшируй ссылки на узлы, проверяй обязательные `[Export]` references, симметрично подключай/отключай события. Не пересоздавай дерево и не ищи узлы по строке каждый кадр.
- Inventory, экипировка, HP, навыки, награды и прочие игровые результаты остаются серверными. UI посылает намерение и показывает подтверждённое состояние; pending-индикация или визуальный preview не должны выдавать локальное действие за подтверждение сервера.
- Для применимых состояний предусмотрены loading, empty, ready, unavailable/error и pending. Показывай понятную причину недоступности и результат действия. Используй предусмотренное игровым контрактом подтверждение необратимых действий.
- UI-ресурсы и данные предпросмотра не раскрывают hidden professions, условия, счётчики или неизвестный контент. Чисто визуальная задача обычно не требует изменения protocol, persistence или Server/Shared.

## Автономная работа и UX

- Сцену можно открыть для компоновки без подключения к серверу. Для интерактивной проверки запускай её отдельно либо через небольшой preview/workbench в `Content.Client/Tests/UI/`, инстанцирующий ту же рабочую сцену.
- Тестовые данные задавай только отдельным preview-adapter/fixture. Runtime показывает полученное состояние либо честное пустое/недоступное состояние. `_Ready()` UI не начинает сетевое подключение и не требует наличия мира для просмотра.
- Проверь открытие, закрытие, Escape, возврат keyboard focus, порядок Tab, hover/pressed/disabled и доступные горячие клавиши. Сохраняй действующие правила переключения окон и отмены черновиков.
- Настрой `MouseFilter`, focus и существующую блокировку игрового input. Проверяй весь путь: клик/drag по UI, колесо в прокрутке, набор текста и modal не должны отправлять нежелательные RMB movement, LMB attack или игровые hotkeys. Прозрачная неинтерактивная область HUD не должна перекрывать управление миром.
- Используй адаптивную компоновку, перенос текста и прокрутку. Проверь длинные русские подписи, текущий минимальный размер окна и другое поддерживаемое разрешение. Учитывай PC-first и будущий touch: читаемые подписи, различимые состояния и удобные зоны нажатия.
- Обновляй UI по изменениям состояния; таймеры обновляй с необходимой частотой. Не загружай ассеты и не перестраивай списки каждый кадр. Скрытые 3D-preview и тяжёлые эффекты не должны постоянно расходовать ресурсы Mobile renderer.

## Проверка и передача

- Сначала проверь сцену/preview без сервера: дерево видно в редакторе, ресурсы загружаются, layout и применимые состояния работают при resize. Осмотри фактический рендер; headless-запуск сам по себе не подтверждает визуальное качество.
- После интеграции проверь рабочий маршрут открытия, действия, серверный ответ при наличии команд, закрытие, input/focus и повторное открытие. Выбирай relevant smoke-проверки через `code-change-verification`; при C#-изменениях выполни `dotnet build Game.slnx`.
- Если Godot/renderer/server недоступны, явно укажи, что не запускалось. Не заменяй проверку рабочей сцены проверкой отдельного похожего макета.
- В handoff укажи путь рабочей `.tscn`, что править в сцене/Theme/Inspector, как запустить preview и основной игровой сценарий, какие проверки реально выполнены. Отдельная сцена остаётся ресурсом клиента и сама по себе не даёт обновления UI без патча.
